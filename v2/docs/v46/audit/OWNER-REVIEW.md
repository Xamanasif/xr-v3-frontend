## How to read this document

**Two classes.** Every issue below carries exactly one of these:

| Class | Meaning |
|---|---|

| **DEFER — safe to defer** | Phase 0 can proceed without your answer and without inventing a product rule. ## 5. The technology-format completion trigger (T-12)

**Your binding constraint (BC3):** "Published, institution access, Student entitlement, runtime activity and learning completion are five different states. Never derive one from another. The event that marks a format Completed is still open (T-12): 'Completed' is set by the system, never by the Student, and never inferred from a launch."

**What the boards draw (CONFIRMED):**
- B3-03: "Completed means The simulation reports that you finished. You can't mark it yourself."; "No 'I have finished' button."
- B3-04 f2: "Completion reported from the headset (T-12)".
- B3-12 C3: the actor for completion is "System".
- B3-05: per format only; no percentage or overall verdict.
- B3-06: feedback is offered only after that format is Completed.
- B3-10: Usage counts "Completed" only when "reported completed by the simulation or the headset".

**What is open:** which runtime event, per format, counts as completion (T-12, also A-06). Separately, B3-03's script moves WEB to "In progress" after a successful launch, and it is not stated whether a portal "Launch WEB" click alone may set "In progress" (register P3-01 (c)). That second question concerns runtime activity, never completion.

**How the plan prevents completion from being inferred from a launch (no rule invented):**
1. **Completion is its own record** (`FormatCompletion`, Appendix C M17), separate from runtime activity. It is created only by the system completion handler through the test/seed-only `RuntimeReportPort.reportCompletion`.
   - No Student command, launch, session, elapsed time, resource opening, assessment or other format can create it (permission rows CMP-01 SYSTEM, CMP-02 DENY "I have finished", CMP-03 DENY "Infer Completed from a launch, resource or assessment").
2. **Invariants checked after every command in tests** (Appendix D §5):
   - "Only runtime ingestion changes ④ (activity), and only the completion handler writes ⑤ (completion)".
   - "The completion handler never writes ⑤ from a launch, resource, assessment, time or another format".
   - "`canOpenFormat` is unchanged by runtime events".
   - "'Completed' is read only from ⑤".
3. **Read models never derive one state from another.** `formatProgress` shows Completed only when a completion record exists, and `feedbackEntry` requires one.
4. **The committed repository code is neutralised, not adopted.** `1b090c9:v2/packages/domain/src/runtime/utilisation.ts` (lines 183–193, 238–242) treats a `SIMULATION_COMPLETED` event on a launched or started session as COMPLETED. That would silently close T-12. The plan moves it behind a replaceable `CompletionPolicy`, labelled interim, for a future runtime adapter only. The mock and every screen ignore it, and `FormatProgressStatus` is the only status a screen uses.

**Classification:**

| Item | Class | Why |
|---|---|---|
| The T-12 trigger event itself | **DEFER** (decide before production; Phase 3 builds on the stand-in) | Phase 0 needs no trigger: completion enters only through the test/seed stand-in, so no rule is invented. |
| Storing completion as a system record behind `CompletionPolicy`, keeping the committed `utilisation.ts` rule only as a labelled interim implementation (AD-39, P3-01 (a)/(d)) | **MUST — part of gate G-2 (e)** | It amends committed ARCHITECTURE §8 ("progress … derived, never stored as truth"), which needs your authorisation. You may also tell us to remove the committed `SIMULATION_COMPLETED` rule instead of keeping it as an interim; the plan works either way. |

## 6. Should shared frontend state survive a refresh and work across tabs?

**Background.** BC14 requires one connected application state for every shared record. BC10 excludes *backend* persistence and requires typed mock services. Board B8-06 says "Real auth, payment, XR runtimes, grading automation and persistence stay out until decided" (register HB-21). The question is whether the in-browser sample world may be kept in browser storage. Source: Appendix D §3 (AD-07), register P0-02.

| Option | What it does | Advantages | Disadvantages |
|---|---|---|---|
| **A · In memory, one world per tab** (plan default) | The world is built from the seed when the tab opens. Every role who signs out and signs in within that tab shares it. Nothing is written to browser storage except the board-drawn selection basket and the request-status ticket (`sessionStorage`). | Fits BC10 and B8-06 as written; needs no authorisation. Deterministic: every load starts from the same seed, which makes tests and demos reproducible. Simplest code and lowest risk; no stale or corrupt stored data. | A refresh resets the walk to the start, so a reviewer must re-walk Flows A–F from Flow A. A second tab gets its own separate world. A deep link opened in a new tab asks for sign-in again. Cross-role continuity (BC14) holds only inside one tab. |
| **B · Versioned `localStorage` snapshot + BroadcastChannel + Web Locks** (TE-6) | One world per browser, saved after every command. All tabs of that browser read the same world and update each other. Writes are serialised. Unreadable or incompatible data reseeds. | Survives refresh. Several tabs can each be signed in as a different role and watch one another update, which is the best experience for cross-role reviews. Still no server or database. The pattern was already proven in the Slice-1 world store (non-visual logic). | Conflicts with B8-06 "persistence … stay out until decided" and FUNCTIONAL_PARITY_MATRIX §G, so it needs your authorisation and exception TE-6. More code: schema versioning, integrity checks, reseed, cross-tab locking. Stored state can drift from the seed and make tests order-dependent unless reset. Per browser only, so reviewers on different machines do not share a world. |
| C · Server-side world in Next.js route handlers | One world on the server | Shared across browsers and devices | **Rejected.** Makes `apps/web` the business backend (ARCHITECTURE §3), invents API paths before `apps/api` exists, is lost on restart and unreliable on serverless. |
| D · Mock Service Worker over an HTTP adapter | Intercepts fetch | Exercises an HTTP adapter early | **Deferred.** Invents endpoints and payloads before the API exists, and needs IndexedDB to persist, which raises the same question as B. |

**Recommendation (not a decision).** Build option A in Phase 0 behind a pluggable persistence driver. Authorise option B **before** hosted reviewer walk-throughs of cross-role flows (the Phase-1 review), if reviewers need refresh survival and multiple tabs.

**Classification: DEFER** (decide by the Phase-1 review). Option A needs no authorisation and invents no rule. Choosing option B later only swaps the driver: no screen, port or domain change.
