- **Design authority and precedence.** Owner binding constraints (`design/handoff-v46/START-HERE.md` BC1–BC14) → the frozen v46 boards → the handoff JSON. Where the JSON index differs from the drawn behaviour, the approved board takes precedence and the discrepancy is documented (owner, 12 Oct 2026). - **Roles (BC1).** Seven authenticated roles — Student, Faculty, **Institute Admin**, Vendor, Academic Reviewer, Content Manager, Super Admin — and the Public surface, which is not a role. - **Hierarchy (BC2).** Engineering area (catalogue grouping) → Course → Experiment → Technology format. Programme is an attribute of the Student record only — not a navigation level, entity, filter or grouping — and there is no Module layer.

- **Recorded exceptions.** `OPEN_DECISIONS.md` Part E (TE-1…TE-8): TE-1, TE-2, TE-5 and TE-7 are approved for Phase 0; TE-8 is approved for Phase-1 Package 1B (14 Oct 2026); TE-3 and TE-4 are drafted for later phases; TE-6 (browser persistence) is not authorised.
- **Evidence.** The audit deliverables, the candidate permission matrix and the Understand-stage evidence are in `docs/v46/` (candidate — owner review).

## 1 · Why V2 exists

The gold-standard prototype proves the B2B behaviour: seven roles, one content source, request → approval → activation, derived entitlement, licence accounting, per-technology progress, runtime telemetry, content production and later-version release. It does so as a dependency-free browser application whose "backend" is an 11,000-line state engine over `localStorage`, with 2,202 deterministic assertions behind it.

That is the right shape for validating product rules and the wrong shape for a production system: no server, no authentication, no authorization boundary, no database, no transport, and no API that a native AR / VR / MR client could report to.

V2 is the production-oriented engineering foundation for the **same product**. It keeps the validated behaviour — through the parity process in `MIGRATION_STRATEGY.md` and `FUNCTIONAL_PARITY_MATRIX.md` — and replaces the execution model. It is also the base for a fresh visual product experience, which is a **later, separate phase** (Design V2). Phase 0 deliberately contains no product screens.

## 3 · Topology and hard boundaries

```
  Browser ──▶ Next.js Web (apps/web) ──▶ Platform API (apps/api) ──▶ Application services
                                                                        │
  AR app ───┐                                                           ├──▶ @xr/domain  (pure rules)
  VR app ───┼──────────────────────────▶ same API                       ├──▶ Prisma (packages/database)
  MR app ───┘                                                           │        └──▶ PostgreSQL
                                                                        └──▶ Object storage · IdP · …
```

| Rule                                                                    | Consequence                                                                                                                                                                                                                                                                              |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **The API is the only authority for business rules and authorization.** | The web application hides what a user may not do; the API **refuses** it. A request that bypasses the UI meets the same rule.                                                                                                                                                            |
| **Next.js is not the business backend.**                                | No Prisma, no database credential, no business rule in `apps/web`. Server components and route handlers call the API with the user's token; client components call it through TanStack Query against the same OpenAPI contract.                                                          |
| **One API for every client.**                                           | Native XR runtimes report to the same versioned REST API the web uses. There is no second ingestion path.                                                                                                                                                                                |
| **Only the API's data layer touches PostgreSQL.**                       | `packages/database` is a dependency of `apps/api` only — enforced (§6).                                                                                                                                                                                                                  |
| **OpenAPI is the external contract.**                                   | TypeScript types shared through `@xr/contracts` are a convenience for TypeScript clients; they never replace the OpenAPI document, which is what a Unity / Android / Swift client codes against. The document is generated from the **same** schema objects the API validates with (§5). |
| **The API is stateless.**                                               | Identity lives in tokens issued by the IdP; long-running work (imports, reminders, telemetry projections) moves to jobs in a later phase.                                                                                                                                                |

> **Amendment (v46, ADR-0002, exception TE-2).** In sample mode the frontend evaluates `@xr/domain` rules in the browser through typed mock services in a separate package, `@xr/sample-platform`, imported only by the composition root. The rules themselves stay in `@xr/domain`; screens decide nothing and render the actions a port offers. The API remains the authority once `apps/api` serves the ports (TE-2 removal trigger).

Enforcement (`packages/config/eslint/boundary-matrix.mjs` is the single declaration):

1. **ESLint rule `xr/resolved-boundaries`** (`packages/config/eslint/rules/resolved-boundaries.mjs`) — every package's flat config includes `boundaries('<package>')`. The rule classifies each `import … from`, `export … from`, `export * from`, `import("literal")` and `import("literal").Type` by its **resolved filesystem target**: a relative or aliased path that lands inside another package's tree is always an error (a package is reached through its public exports only); a bare workspace specifier must be allowed by the matrix, must not name `src/` or `dist/`, and must resolve through the target's `exports` from the importing file; third-party targets are matched against the package's forbidden patterns (web ✗ Nest / Prisma; domain ✗ everything; API ✗ React / Next / UI) whether written as a bare specifier or as a path that resolves into a `node_modules` directory — the target's real path decides ownership: the external package named by the last `node_modules` segment (scoped names take two segments; pnpm's `.pnpm` store paths resolve identically), confirmed by that package's own `package.json`, so `../../../apps/api/node_modules/@nestjs/common/index.js` is judged exactly as `@nestjs/common`; a workspace package reached through some `node_modules` link is still that workspace package, and a `node_modules` path with no package identity is an error. `require()` is not analysed: this is an ESM-only workspace.
2. **Dependency-matrix and build-graph test** — `packages/config/src/boundaries/boundaries.test.ts` reads every workspace `package.json` and every `tsconfig.build.json`, fails when a package declares a workspace dependency it is not allowed or references a project it does not depend on, and lints fixtures through the rule — named, relative, aliased, dynamic and type-only forms, including the demonstrated bypass `domain → ../../database/dist/…`.
3. **Package `exports`** — deep paths such as `@xr/contracts/src/x` do not resolve at all.

> **Amendment (v46, ADR-0002, ADR-0008).** Two additions, each made with its boundary-matrix row, `WorkspacePackage` union entry and tests in the implementing work package: `@xr/contracts` gains a `./draft` subpath export for the typed service ports, DTO schemas and a framework-free contract suite (AD-02); a new package `@xr/sample-platform` (may depend on `@xr/contracts`, `@xr/domain`, `@xr/validation`; forbids framework-server, framework-web and data-layer packages) holds the mock adapter (AD-01). `@xr/domain` stays zero-dependency and zod-free.

## 7 · Multi-tenancy

| Rule                                                                                                                                                                                                                          | Basis                         |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| An institution is a **tenant**. A campus or operational unit may be its own tenant; there is **no sub-tenant level**.                                                                                                         | `STK31-23`                    |
| Two planes: the **central content plane** (Vendor, Academic Reviewer, Content Manager) and **tenant planes** (Tenant Admin, Faculty, Student). The **Super Admin spans both**, with the only cross-tenant access (FRD 1.3.5). | PM-13, `STK31-21`, `STK31-40` |
| Analytics and reporting never cross a tenant.                                                                                                                                                                                 | FRD 1.3.4                     |
| B2C individual learners are the **same Student/Learner role in a non-institutional context**; deferred, but the model must not preclude a person without a tenant.                                                            | `STK31-01`, `STK31-04`        |

**Isolation strategy (engineering judgement, reversible):** one PostgreSQL database with a shared schema; every tenant-plane table carries a `tenant_id`; every repository method on the tenant plane requires a `TenantContext` and scopes its queries by it; the Super Admin's cross-tenant reads go through explicitly named, audited operations rather than an unscoped repository. PostgreSQL row-level security as defence in depth, and the FRD 1.3.2 wording about a _separate B2C database environment_, are open engineering decisions (E-04). The gold standard proves the invariant this must preserve: _one institution never writes into another_ (QA scenario R).

## 8 · Data boundary

Records are classified by who governs them, not by which screen shows them. The 26-record conceptual model in `ui-ux/17-stakeholder-correction-blueprint/17_CONCEPTUAL_DATA_AND_STATE_MODEL.md` and the gold-standard state model (`README.md` › _State model_) are the inputs; **the production schema is a later phase** and is not derived by translating `localStorage` collections into tables.

| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Platform-canonical                 | AcademicGrouping, Course (+ canonical code), Experiment / content record, ContentVersion, PublishedContent, platform role scopes, Tenant, TenantRequest, TenantContentAccess, AccessTerm, LicenceQuantity | Super Admin · Content Manager · Academic Reviewer · Vendor, each within `STK31-08` / `STK31-09` / `STK31-41` |
| Institution-governed               | TenantUser (+ provenance `erp` / `csv` / `manual`), UserGroup, TenantCourseMapping (local code, optional Semester), FacultyMapping, ExperimentAssignment, SSO / ERP configuration                         | Tenant Admin (`STK31-25`, `STK31-26`, `STK31-11`)                                                            |
| Faculty-governed                   | AssessmentDefinition, Question (Add / Edit / **Delete** with history preserved), DescriptiveReview, visibility policy                                                                                     | Faculty (`STK31-30…34`)                                                                                      |
| Learner-generated                  | ResourceActivity, AssessmentAttempt (with its question snapshot), DeviceTransferRequest, SupportRequest                                                                                                   | the Student                                                                                                  |
| Runtime-generated                  | `runtime_events` — append-only, client-minted idempotency key, two clocks                                                                                                                                 | Web / AR / VR / MR runtimes through the ingestion endpoint                                                   |

Persistence principles carried from the validated behaviour: prefer reversible status over deletion (`STK31-22`); every governance act writes who / when / why; a published artefact is never rewritten under its own version label (Implementation 09 §6); a completion is never walked back by a later run; a refused event is not stored.

> **Amendment (v46, ADR-0006).** One record is stored as a system fact rather than derived: **learning completion per technology format** (`FormatCompletion`), written only by the system completion handler, never by a Student command and never from a launch. Progress views remain derived per format. The v46 names apply to the frontend: the course grouping is the **Engineering area** (B7-07); Programme is held on the Student record only (BC2).

## 9 · Authorization boundary

Authorization is decided in the API's application layer, before any use case runs, from a **Principal** resolved server-side:

```
Principal { subject, personId?, tenantId?, roles: [ { role, plane, scope } ] }
   role  ∈ student | faculty | tenant_admin | vendor | academic_reviewer | content_manager | super_admin
   plane ∈ platform | tenant
   scope ∈ all | course:<id> | experiment:<id>          (platform roles — STK31-41)
```

Roles and scopes come from the platform's own records (role assignments, Tenant Admin assignment, tenant membership), **not** from IdP claims alone (FRD diagram D11: SSO → tenant → role resolution). Policies encode the confirmed boundaries: a Vendor never publishes (FRD 1.4.5); first publication is the Content Manager's, later-version Release / Hold is the Super Admin's (`STK31-06/07`); a Tenant Admin cannot assign outside the approved set nor redefine the catalogue (`STK31-24`, `STK31-10`); a Student never configures an assessment or sees an answer key (PM-15, D-25). Phase 0 defines the seam (`AuthModule`, `TenancyModule`) and the `Principal` type only.

## 10 · Authentication boundary

| Element           | Direction                                                                                                                                                                                                                  |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Protocol          | OIDC / OAuth 2.0. The platform's API verifies bearer access tokens (JWT, JWKS discovery) issued by an identity layer the platform trusts.                                                                                  |
| Institutional SSO | Institutions with SSO federate through that identity layer (SAML or OIDC upstream); institutions without SSO use platform authentication (`STK31-44`). Attribute mapping and password policy are pending details.          |
| Web sessions      | Next.js acts as the relying party (authorization code + PKCE). Whether the browser holds tokens or a server-side session with a BFF cookie is an open engineering decision (E-02).                                         |
| Native XR clients | Sign in as the Student against the same identity layer (authorization code + PKCE, or device authorization for headsets — E-03), then fetch entitlements and report runtime events (`RUNTIME_INTEGRATION_CONTRACT.md` §8). |
| Identity ↔ role   | Who a person _is_ comes from the IdP; what they may _do_ comes from platform records (§9).                                                                                                                                 |
| **Phase 0**       | No authentication is implemented and none is faked. The final identity product / provider is open (see `OPEN_DECISIONS.md`).                                                                                               |

> **Amendment (v46, ADR-0003, exception TE-1).** In sample mode a session port over sample-world people stands in for authentication: the session holds only a person id; there are no tokens and no secrets; there is no account or role switcher and no DEMO banner anywhere. Phase 0 reaches the shells through a CI-only boot descriptor; the designed sign-in form (XS-01) follows in Phase 1. The statement "no authentication is implemented and none is faked" stays true for production.

## 11 · XR runtimes and telemetry

The runtime contract validated in Implementation 09 is carried unchanged in meaning:

- five events — `SIMULATION_LAUNCHED`, `SESSION_STARTED`, `SESSION_ENDED`, `SIMULATION_COMPLETED`, `SIMULATION_ERROR` — and **no content event**;
- a client-minted `clientEventId` (idempotent retry), a required `sessionId`, two clocks (`occurredAt` from the runtime, `recordedAt` from the platform), ISO-8601 enforced on the wire by an exact pattern and normalised to UTC on acceptance;
- ingestion accepts an event only if the Student may run that technology of that Experiment **at that moment** — the same predicate that gates a launch;
- a simulation is complete for a technology **only** when a `SIMULATION_COMPLETED` event exists for a session that was actually opened; nothing else completes it — not time, resources, video, assessment, or another technology;
- progress is expressed **per technology** (`STK31-36`); no aggregate with a technology denominator is shown while D-09-13 is open.

V2 shape (later phase): `POST /api/v1/runtime/events` accepting batches; an append-only `runtime_events` table keyed by `(personId, experimentId, technology, clientEventId)`; an incremental projection replacing the prototype's whole-log refold. `@xr/domain` carries the vocabulary and the completion predicate today, with the "what cannot complete a simulation" table as unit tests; `@xr/contracts` carries the **draft** wire schema of the event, already verified representable in OpenAPI. Open: the per-technology completion condition (R1 / D25), retention (R2), clock-trust policy (R7), revocation (R8), offline reconciliation (R9).

> **Amendment (v46, ADR-0006).** The completion predicate above is kept as a **labelled interim implementation** behind an injectable `CompletionPolicy`; it does not decide T-12 / `OPEN_DECISIONS.md` A-06, which stays open. In sample mode completion enters only through the test/seed-only runtime report stand-in; nothing a Student operates can complete a format.

## 14 · Environments, configuration and cache correctness

Three environment concepts — `development`, `staging`, `production` — expressed as the `APP_ENV` value and validated by `@xr/config/env`. Configuration is **data supplied at boot**, never prototype flags scattered through code: no scenario selector, no demo clock, no stand-in controls in V2. Secrets are placeholders in `.env.example` only; a secret manager is chosen with the hosting decision (E-08).

Turborepo runs in **strict env mode**: only declared variables reach a task, and only `CI` passes through globally. Environment handling is package-local: the web build (`apps/web/turbo.json`) hashes `NEXT_PUBLIC_*` and every `.env*` file Next.js can load (`.env`, `.env.local`, `.env.development`, `.env.development.local`, `.env.production`, `.env.production.local`), so an ignored file cannot make cache reuse accidental; unrelated variables such as `DATABASE_URL` do not touch its hash. Unit `test` tasks are cacheable because they are **environment-independent by construction** — the shared Vitest factory blanks `DATABASE_URL` for them; database-backed checks run through the uncached `test:db` task, which declares `DATABASE_URL`. `test:e2e` and `dev` are never cached and receive only the runtime variables they need.

> **Amendment (v46, ADR-0007, exceptions TE-5 and TE-7).** Two public build flags — `NEXT_PUBLIC_XR_DATA_SOURCE` (`sample` | `api`) and `NEXT_PUBLIC_XR_TEST_HOOKS` (CI/Playwright builds only) — are read once through `@xr/config/env`. Sample mode runs on a sample clock anchored to a sample "today"; time travel, fixture worlds, test sessions and fault injection exist only through CI test hooks. The product still has **no scenario selector, no demo clock and no stand-in controls**. Turbo's local cache is pinned to `v2/.turbo/cache` (`turbo.json` `cacheDir`) so runs from a linked git worktree never write into another checkout.

Fastify's structured (pino) logging with a request id on every log line and on every problem-details response. Metrics and tracing (OpenTelemetry, or NestJS 12's `@nestjs/observe`) are deferred to the hosting decision.

## 17 · Explicitly not in Phase 0

## 18 · Deployment prerequisites — recorded, not built

Identified by the independent audit as legitimate and deferred; each is a bounded piece of engineering to complete **before the first deployed environment**, tracked as `OPEN_DECISIONS.md` D-01…D-05:

- separate **liveness** and **readiness** endpoints (today one health route serves both, with `database=skip` as the cheap poll);
- **production configuration enforcement** — refuse to boot in `production` without the values production requires (issuer, storage, database), rather than defaulting;
- **graceful shutdown** — Nest shutdown hooks, connection draining, in-flight request completion;
- **unified request-correlated logging** — one logger for Nest and Fastify with the request id on every line;
- **secret management and CI/CD** — with the hosting decision.
