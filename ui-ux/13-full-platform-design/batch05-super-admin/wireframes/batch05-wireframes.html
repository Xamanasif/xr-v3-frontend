WIREFRAMES — STRUCTURE ONLY · BATCH 05

Super Admin and platform-wide administration — structural wireframes

Layout and content structure for the ten Batch-05 screens. These describe what goes where and what each state says — the interactive prototype in ../prototype/ is the reviewable artefact. Every institution, person, identifier, module, version and date shown is sample design data, and all five institutions are fictional.

Screens

  1. Platform overview
  2. Institutions
  3. Institution detail
  4. Module releases
  5. Release decision
  6. Device replacement requests
  7. Device request detail
  8. Licensing
  9. Platform roles
  10. Platform configuration
There is no publication anywhere in this batch — deliberately. The Content Manager publishes content (PM-16 · PM-17 · PM-18, 25 August 2026). The Super Admin holds no publish control, no publication queue, no approve-content, no return-to-vendor and no request-changes action, and none is invented in its place. FRD 1.4.4 still assigns publication to the Super Admin; that is a recorded deviation, left unreconciled in the sources. Whether the Super Admin may return a submission at the publication gate is QP-26, OPEN, and stays open. Every mention of publication in these wireframes is historical explanation or an explicit boundary note — never a product action.
The shell is Batch 01’s, adapted only where a capability changed. Prototype strip → top bar (logo · platform name · account) → left navigation → scope bar → breadcrumb → page head → content. The navigation is Overview · Institutions · Releases · Device requests · Licensing · Platform (with Platform roles and Configuration beneath it) — six primary items, depth two at most, the same shape as the Institute Admin workspace in Batch 03 so the two read as one platform. Table 41’s pre-override navigation read “Overview · Publishing · Content · Institutions · Licensing · Platform · Account”: Publishing is struck (PM-16/17/18, nothing replaces it), Content is struck (a second content catalogue would duplicate the Content Manager’s CM-03), and Releases is added (FRD 2.3.2 has a Phase-1 surface and had no navigation entry of its own).
There is no institution chip in the global chrome, on any screen. FRD 1.3.5 and PM-13 place this role above every tenant; an institution name in the top bar would imply a current tenant this role does not have. An institution appears only in the scope bar, inside the page, and only while one is open — which is SA-03 and nowhere else. The scope bar has exactly two forms: Viewing · The platform, and the tinted Viewing institution · <name>. That is the structural half of AC-04: the moment of crossing into a tenant is never invisible.

The three states are derived, never stored. The platform holds no lifecycle label for an institution, because no requirement defines one. State is recomputed on every render from three observable readiness facts — content access (FRD 6.2.1), institutional sign-in (FRD 4.2.2), institution data (FRD 7.1.1 · 7.2.1). There is deliberately no inactive, suspended, expired or cancelled state: each would be the result of an administrative action this role has no source authority to take.

Absent by design: KPI tiles · charts · trends · percentages · learner counts · student caps · seat or capacity figures (OQ-03 is OPEN) · league tables · any figure that spans two institutions. The two numbers that do appear are the same two the navigation shows, and both count work awaiting this role.
