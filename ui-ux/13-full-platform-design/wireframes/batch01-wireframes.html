XR Simulation Learning Platform — Batch 01 Wireframes

Structural validation of Flow A (Content to Production: Vendor → Academic Reviewer → Content Manager → Super Admin) and Flow B (Entitled XR content to learner device). One shared shell, role-based workspaces. Statuses use the approved vocabulary; the XR delivery mechanism is deliberately unselected, so all device copy is mechanism-neutral. High-fidelity behaviour lives in ../prototype/batch01-prototype.html.

Validates

  1. One shell, seven roles later. Header (64px) with logo + product name; account control right; Help in a consistent location.
  2. Workspace context is an explicit label atop the side nav (e.g. “VENDOR · Sample XR Content Vendor”). No workspace switcher is invented.
  3. Side navigation is minimal and role-specific; governance roles land on their queue.
  4. Detail pages use content + rail; the rail always carries workflow position, the current role's action, and history — same slots for all four governance roles.
  5. In the prototype only, a clearly-labelled dark strip above this shell provides role jumping: “Prototype Navigation — Not Product UI”.

Flow A — Content to Production

Vendor creates and submits → Academic Reviewer validates or requests changes → Content Manager approves readiness or requests changes → Super Admin publishes. Returns go to the vendor with a reason; resubmission re-enters review at the returning gate. Review history is traceable throughout. No one but Super Admin can publish; the vendor never can.

Screen sequence: S01 Submissions → S02 New Submission → S03 Detail (submit) → S04 ARV Queue → S05 Academic Review [approve | changes required ↩ S03 → correct → resubmit → S04] → S06 CM Queue → S07 Readiness Review [approve | changes required ↩ S03] → S08 Publish Queue → S09 Publish → S10 Published

Flow B — Entitled XR content to learner device

Published experiment → learner entitlement → device compatibility → “Get on device” → availability states → run on supported device → completion pending → completion received → progress updated. The delivery mechanism is not selected; every state below is mechanism-neutral and none implies the browser is watching the headset.

Screen sequence: S11 My Learning → S12 Experiment Detail (entitlement ✓ · device ✓) → S13 XR Device Access (Get on device → Availability pending → Ready on device → run on device → Completion pending → Completion received) → S14 Progress updated. Failure branches on S12 (not entitled · access denied · unsupported device) and S13 (availability failed · availability unknown).

Annotations

  2. Waiting is designed: honest indeterminate copy, no fake percentages, no transport detail (nothing about stores, APKs, pairing, sync).

  4. Every failure state says what happened, whether the learner can recover, the available action, and when support is appropriate.
